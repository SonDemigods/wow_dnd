## 循环依赖分析

### item-template ↔ inventory 循环风险

**问题**：若 item-template/db.ts 改为 `@/modules/inventory`（即 inventory/index.ts），会形成运行时循环：

```
inventory/index.ts
  → inventory/store.ts（re-export）
    → @/modules/item-template（unifiedItemTemplateCache）
      → item-template/index.ts
        → item-template/db.ts
          → @/modules/inventory（循环回到起点）
```

**结果**：Vite/ESM 模块加载器在循环加载时返回部分加载的模块，`inventoryDbService` 可能为 `undefined`，导致运行时错误。

**解决方案**：item-template/db.ts 直接引用 `../inventory/db`（inventory/db.ts 不依赖 item-template），保持单向依赖。

### type-only import 的循环依赖风险

**问题**：若 `inventory/types.ts` 的 `import type { Stats } from '../character/types'` 改为 `from '@/modules/character'`（即 character/index.ts），TypeScript 在解析 character/index.ts 时会遍历所有 export，包括 character/store.ts 的导出类型。character/store.ts 通过 CharacterLifecycleService 间接引用 inventory 类型，形成类型解析循环：

```
inventory/types.ts
  → @/modules/character（character/index.ts）
    → character/store.ts（类型解析）
      → CharacterLifecycleService（类型解析）
        → @/modules/inventory（inventory/index.ts）
          → inventory/store.ts（类型解析）
            → @/modules/item-template（类型解析）
              → ...
```

**结果**：虽然 `import type` 在编译后擦除，但 TypeScript 类型检查阶段可能因循环引用出现 "cannot be referenced from another file's type before initialization" 错误。

**解决方案**：type-only import 保留相对路径 `../xxx/types`，因为：
1. `import type` 编译后完全擦除，运行时不触发模块加载
2. types 文件之间的依赖是模块内部的实现细节，不影响公共 API
3. 改成 `@/modules/xxx` 不增加工程价值，反而引入类型解析循环风险
