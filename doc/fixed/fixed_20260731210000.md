## 已修复问题

### P3-139. TalentEffect 类型拆分 + hp_max 配置 bug 修复 — 中等风险

**问题背景**

原 `TalentEffect` 接口的 `stat` 字段类型为 `keyof Stats | string`，过于宽松导致两类问题：

1. **类型不安全**：`stat_bonus` 与 `resource_bonus` 共用同一 `stat` 字段，但合法值集合完全不同（基础属性 str/dex/con/int/wis/cha vs 资源上限 rage_max/mana_max/energy_max 等）。配置时拼写错误无法在编译期发现。

2. **配置 bug 静默失效**：`config_class_talents.ts` 中 `warrior_prot_t3`（壁垒）与 `evoker_pres_t3`（生命赐福）配置为 `{ type: 'stat_bonus', stat: 'hp_max', valuePerRank: 0.05 }`，但：
   - `hp_max` 不是 `keyof Stats`，`getTalentStatBonuses` 仅读取 `validStatKeys = ['str','dex','con','int','wis','cha']`
   - 该天赋效果被静默丢弃，玩家学习后无任何实际效果
   - 同时污染 `summary.statBonuses['hp_max']`（虽无人消费）

**涉及文件**

  - 新增 `ResourceStatKey` 类型（`${ResourceType}_max` 联合）
  - 拆分 `TalentEffect` 为可辨识联合：`StatBonusEffect` / `ResourceBonusEffect` / `SkillEnhanceEffect` / `SpecialEffect` / `SimpleMultiplierEffect`
  - `StatBonusEffect.stat` 收窄为 `keyof Stats`
  - `ResourceBonusEffect.stat` 收窄为 `ResourceStatKey`
  - 新增 `hp_multiplier` 类型（属 `SimpleMultiplierEffect`）

**修复方案**

1. **类型拆分**：将 `TalentEffect` 从单一 interface 改为可辨识联合类型（discriminated union），每个分支有独立的必填字段。TS 编译器自动收窄每个 case 的 effect 形状，不再需要运行时 `if (effect.stat)` 守卫。

2. **配置 bug 修复**：新增 `hp_multiplier` 效果类型，语义为"每级提升 X% 生命上限"，与 `damage_multiplier` / `healing_multiplier` 同属 `SimpleMultiplierEffect` 分支。原 `stat_bonus + hp_max` 的错误配置改为 `hp_multiplier`。

**设计决策**

- 选择新增 `hp_multiplier` 类型而非扩展 `Stats` 接口：`Stats` 仅含 6 大基础属性（str/dex/con/int/wis/cha），HP 是由 con 派生的衍生属性，不应进入 `Stats`。`hp_multiplier` 语义更准确（百分比倍率，非绝对值加成）。
- `ResourceStatKey` 定义为 `${ResourceType}_max` 模板字面量类型，与 `config_class_talents.ts` 中已有的 `rage_max` / `mana_max` / `energy_max` / `soul_shard_max` / `chi_max` 配置完全对齐。
- `hpMultiplier` 字段目前无消费方（与 `damageMultiplier` / `critBonus` / `resourceBonuses` 同属"已聚合未应用"状态），后续可在 character/store.ts 的 `recalculateHpMp` 中消费，应用 `maxHp * (1 + hpMultiplier)` 提升 HP 上限。
