## 一、业务逻辑修复（14 个）

### BIZ-1：玩家技能单目标分支不应用暴击 【P0·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/combat/composables/usePlayerAction.ts:445`、`369` |
| 类型 | 业务逻辑错误（战斗） |

**问题表现**：单目标与 AOE 技能分支中 `addCombatLog` 调用时 `isCrit: false` 被硬编码，`processDamagePipeline` 内部的暴击判定结果未回传给日志层。

**可能影响**：玩家施放任何技能都不会触发暴击，暴击率属性对技能完全无效，严重削弱法师/术士等技能型职业的输出上限，使「法术致命」等暴击类被动形同虚设。

**修复方案**：在技能伤害分支调用 `processDamagePipeline` 前先执行 `rollCritical` 判定暴击，将暴击结果作为 1.5 倍乘数传入管线，并同步到 `addCombatLog` 的 `isCrit` 字段。单目标和 AOE 分支均应用此逻辑。

### BIZ-2：敌人伤害类型硬编码为物理 【P0·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/combat/composables/useEnemyAction.ts:76` |
| 类型 | 业务逻辑错误（战斗） |

**问题表现**：`applyEnemyDamageToPlayer` 中 `processDamagePipeline` 的 `damageType` 参数硬编码为 `'physical'`，无论敌人使用物理攻击还是魔法技能（如 `shadow_bolt`、`frost_breath`）。

**可能影响**：敌人魔法技能也走物理防御减免，玩家魔法防御属性对敌人法术完全无效；法系 Boss 难度被严重低估。

**修复方案**：新增 `mapSkillTypeToDamageType` 函数，根据敌人技能 `type` 字段动态传入 damageType（`magic_damage` → `'magical'`，`physical_damage` → `'physical'`），普通攻击默认物理。`applyEnemyDamageToPlayer` 增加 `damageType` 参数由调用方传入。

### BIZ-3：敌人速度兜底使用 dodgeChance 【P0·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/combat/composables/useInitiative.ts:81` |
| 类型 | 业务逻辑错误（战斗先攻） |

**问题表现**：`enemySpeed = e.stats?.dex || e.dodgeChance || 5`，当 `stats.dex` 为 0 或 undefined 时用闪避率作为速度兜底。

**可能影响**：先攻排序严重失真，silithid（dodgeChance=10）比 ogre（dodgeChance=3）先攻更快，与设计意图不符。

**修复方案**：移除 `dodgeChance` 兜底，改为 `e.stats?.dex ?? 5`。

### BIZ-4：DOT 杀敌不触发胜利判定 【P0·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/combat/composables/useInitiative.ts`（tickAllEffects，约 227 行） |
| 类型 | 业务逻辑错误（战斗结算） |

**问题表现**：`tickAllEffects` 中 DOT 造成玩家死亡时触发 defeat 判定，但 DOT 杀死敌人时仅检查玩家死亡，不触发 victory 判定。

**可能影响**：战斗节奏拖沓；极端情况下若所有敌人都被 DOT 杀死但 victory 未触发，玩家可能陷入无敌人可打的死局。

**修复方案**：在 `tickAllEffects` 中 DOT 结算后检查所有敌人 HP，若全部 ≤0 则调用 `endCombat('victory')`。

### BIZ-5：被动技能 stat_modifier/damage_reduction/buff 三类效果无实际作用 【P0·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/combat/composables/usePassiveSkills.ts:140-155` |
| 类型 | 业务逻辑缺失（被动系统） |

**问题表现**：注释明确标注"预留扩展点"。`stat_modifier`（魔法攻击力+10%）、`damage_reduction`（低血减伤 20%）、`buff`（附加 DOT）三类效果仅记录日志，不修改任何属性或注入效果容器。

**可能影响**：13 个职业共 39 个被动中，约 20+ 个被动完全无效。玩家花精力选择职业却感受不到被动差异。

**修复方案**：为 `stat_modifier` 在 `createPlayerEffectContext` 中累加 multiplier；为 `damage_reduction` 在 `processDamagePipeline` 防御阶段应用减免；为 `buff` 调用 `addEffectToContainer` 注入对应 DOT 效果。

### BIZ-6：BOSS 机制标记设置但无消费代码 【P0·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/boss/engine.ts:93-115` |
| 类型 | 业务逻辑缺失（BOSS 战） |

**问题表现**：`invulnerable`、`charge_attack`、`revive`、`counter_stance`、`steal_buff`、`split` 六种机制执行器仅设置标记位，combat store 中没有任何代码消费这些标记。`stun_player`、`silence_player`、`arena_hazard`、`split` 执行器是空函数。

### BIZ-7：enrage 机制可无限叠加 【P0·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/boss/engine.ts:71-74` |
| 类型 | 业务逻辑错误（BOSS 数值） |

**问题表现**：`enrage` 执行器每次触发都执行 `boss.physicalAttack = Math.round((boss.physicalAttack || 10) * multiplier)`，`intervalTurns: 1`，无"已激活"标记或上限保护。

**可能影响**：每回合物理攻击力 ×1.5，10 回合后攻击力变为初始的 57.7 倍，BOSS 战拖久必败，玩家无法打持久战。

**修复方案**：在 `BossRuntimeState` 增加 `enraged?: boolean` 标记，enrage 执行器检查已激活则跳过。

### BIZ-9：双重死亡处理与复活 【P0·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/character/store.ts`（takeDamage + endCombat defeat） |
| 类型 | 业务逻辑错误（角色状态机） |

**问题表现**：`takeDamage` 内部检测 `isDead` 后自动调用 `handleDeath`（复活，HP/MP 至 50%，经验清空）。同时 `combat/store.ts` 的 `endCombat('defeat')` 也会调用 `characterStore.handleDeath()`。

**可能影响**：玩家死亡时可能被复活两次，经验被清空两次；`takeDamage` 内部自动复活会导致战斗尚未结束玩家就已复活，战斗状态机错乱。

**修复方案**：`takeDamage` 仅扣血和标记 `isDead`，不自动复活；复活逻辑统一由 `endCombat('defeat')` 调用。exploration 模块 3 处死亡检查同步更新。

### BIZ-10：资源系统生成但不消耗 【P0·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/combat/store.ts:358-387` + `src/modules/skill/types.ts` |
| 类型 | 业务逻辑缺失（资源系统） |

**问题表现**：`canCastSkill`/`consumeSkillResource` 检查 `(skill as unknown as { resourceType?: string }).resourceType`，但 `Skill` 类型定义中从未包含 `resourceType` 字段。资源系统的 `generate`/`onAttack`/`onKill` 钩子正常执行（资源会增长），但 `consume` 永远不会触发。

**可能影响**：战士怒气、潜行者能量+连击点、术士灵魂碎片、武僧真气永远无法被消耗，资源系统沦为摆设。

**修复方案**：在 `Skill` 接口增加 `resourceCost?: { type: ResourceType; amount: number }` 字段；在 `canCastSkill` 中同时检查 `mpCost` 和 `resourceCost`；在 `castSkill` 成功后调用对应资源系统的 `consume`。

### BIZ-13：套装效果计算但从未应用 【P0·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/equipment/store.ts`（activeSetBonuses computed） |

**修复方案**：在 equipment/store.ts 新增 `appliedSetBonuses` ref 跟踪已应用套装奖励，新增 `setBonusEffectToStats` 和 `reapplySetBonuses` 方法实现 diff 应用/移除逻辑。在 `equipItem`/`unequipItem`/`initialize`/`reset` 中调用 `reapplySetBonuses`，通过 `characterStore.applyBonus`/`removeBonus` 应用/移除属性加成。

### BIZ-23：BOSS 阶段阈值排列与注释矛盾 【P0·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/boss/phase-manager.ts:26` + `src/data/config_bosses.ts` |
| 类型 | 业务逻辑错误（BOSS 阶段） |

**问题表现**：注释说"按 HP 阈值降序排列，索引越大阈值越高"，自相矛盾（降序排列意味着索引越大阈值越低）。`findPhaseIndex` 在 HP=0% 时返回索引 2（基础阶段，hpThreshold=0），导致 BOSS 临死时切回"正常"阶段。

**可能影响**：BOSS 死亡瞬间从"濒死挣扎"切回"正常"阶段，`applyPhaseStats` 会用"正常"阶段的 `statMultipliers`（无）覆盖"濒死挣扎"的属性加成，导致 BOSS 死亡瞬间属性回退。

**修复方案**：在 `findPhaseIndex` 中跳过 `hpThreshold===0` 的基础阶段，HP=0 时直接返回最低阈值阶段（濒死挣扎），不切回基础阶段。

## 二、架构修复（2 个）

### ARCH-1：data 模块反向依赖 boss 模块 【P0·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/data/service.ts:19, 224` |
| 类型 | 架构违规（跨层反向调用） |

**问题表现**：data 模块作为最底层持久层基底，反向 import 了 boss 业务模块的 DbService 和类型：

```typescript
import { bossDbService } from '../boss/db';

```

**修复方案**：移除对 `bossDbService` 的运行时 import，仅保留 `BossStorage` 类型 import（编译时移除，不形成运行时依赖）。`initBosses` 方法内联字段转换逻辑（undefined→null、isBoss 固定为 1、falsy 值统一为 undefined），直接调用 `db.config_bosses.bulkPut()` 写入，与 boss/db.ts 的 saveBossTemplate 保持存储格式一致。

## 四、性能修复（1 个）

### PERF-1：N+1 写入模式拖慢初始化 【P0·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/data/service.ts:168-172` |
| 类型 | 性能瓶颈 |

**问题表现**：

```typescript
private async initTable(table: Table, data: readonly unknown[]): Promise<void> {
  for (const item of data) {
    await table.put(item);  // 逐条 await put
  }
}
```

`initTable` 在循环内对每条数据 `await table.put`，被 10 余张配置表初始化复用。

**可能影响**：首启写入 N 条配置 = N 次 IDB 事务往返。若 mobs 500 条、items 800 条，首屏可观察 1-3 秒延迟。

**修复方案**：改用 `table.bulkPut(data)` 单次事务批量写入。增加空数组保护（`if (data.length === 0) return`）。此优化被 10 余张配置表初始化复用，显著降低首启写入延迟。
