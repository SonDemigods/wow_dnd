## P3-144：模板 Map 错用 ref 导致深度追踪

- **问题位置**：
  - [src/modules/inventory/store.ts:92](file:///d:/openSource/wow_dnd/src/modules/inventory/store.ts#L92) `itemTemplates`
  - [src/modules/skill/store.ts:77,80](file:///d:/openSource/wow_dnd/src/modules/skill/store.ts#L77) `skillTemplates`/`monsterSkillTemplates`
  - [src/modules/equipment/store.ts:159](file:///d:/openSource/wow_dnd/src/modules/equipment/store.ts#L159) `equipmentTemplates`
  - [src/modules/quest/store.ts:134,143](file:///d:/openSource/wow_dnd/src/modules/quest/store.ts#L134) `questDefinitions`/`questInstances`
- **修复策略**：
  1. 全部 6 个 Map ref 改为 `shallowRef<Map<string, T>>`
  2. 无原地 mutate 的模块（inventory/quest）直接替换，无需额外改动
  3. 有原地 mutate 的模块（equipment/skill）在 set/delete 后调用 `triggerRef` 显式触发响应式更新；clear 改为整体替换 `new Map()`（赋值自动触发响应式，无需 triggerRef）
  4. `skill/store.ts:loadTemplatesTo` 移除多余的 `clear()`（整体替换前清空是无效操作）
- **关键代码**：
  ```typescript
  // equipment/store.ts — 原地 mutate + triggerRef
  function addEquipmentTemplate(item: EquipmentItem): void {
    equipmentTemplates.value.set(item.id, item);
    triggerRef(equipmentTemplates);  // P3-144：shallowRef 原地 mutate 后显式触发
    equipmentDbService.saveEquipmentTemplate(item).catch(err => {
      equipmentTemplates.value.delete(item.id);
      triggerRef(equipmentTemplates);  // 回滚后同样触发
    });
  }

  // skill/store.ts — clear 改整体替换
  async function loadTemplatesForClass(classId: string): Promise<void> {
    if (!classId) {
      skillTemplates.value = new Map();  // P3-144：shallowRef 整体替换，无需 triggerRef
      return;
    }
    await loadTemplatesTo(skillTemplates, () => skillsDbService.getSkillTemplatesByClass(classId));
  }
  ```
- **效果**：消除 Map 内部深度响应式追踪开销，常驻内存的数百条模板条目不再被递归代理。
- **风险**：低。shallowRef + triggerRef 是 Vue 官方推荐的浅响应式模式；inventory/quest 无原地 mutate，零风险；equipment/skill 的 mutate 调用点已全部覆盖 triggerRef。

## P3-145：CombatPopup v-for 用 index 作 key

- **问题位置**：[src/components/popup/CombatPopup.vue:12,126](file:///d:/openSource/wow_dnd/src/components/popup/CombatPopup.vue#L12)
- **修复策略**：
  1. `bossIntroLines`（字符串数组）：`:key="i"` → `:key="line + '-' + i"`（line 内容 + index 组合键，消除纯 index 在数组重排时的不稳定问题）
  2. `logsReversed`（CombatLog 数组，无 id 字段）：`:key="i"` → `:key="log.timestamp + '-' + i"`（timestamp 毫秒级提供时间维度唯一性，i 兜底同毫秒多日志）
  3. 检查 InventoryPopup/QuestBoardPopup/CharacterInfoPopup 的 v-for：均已用稳定 key（cat.id/stat/slot.key/obj.key），无需修改
- **效果**：战斗日志增长到 20-50 条时，新日志插入头部不再触发全量 DOM diff；2x 战斗速度下减少掉帧。
- **风险**：极低。纯模板修改，不涉及业务逻辑。

## P3-153：exploration currentCharacterId 未对齐 gameStore 代理模式

- **问题位置**：[src/modules/exploration/store.ts:53](file:///d:/openSource/wow_dnd/src/modules/exploration/store.ts#L53)
- **修复策略**：
  1. 引入 `useGameStore`，`currentCharacterId` 从 `ref<string | null>(null)` 改为 `computed<string | null>(() => gameStore.currentCharacterId)`
  2. 删除 `init(characterId)` 中的 `currentCharacterId.value = characterId` 赋值（只读 computed 不可赋值）
  3. 保留 `characterId` 参数用于从 DB 加载该角色的探索数据
  4. 调用方（GameBootstrap/ExplorationView）在调用 `init` 前已通过 character 模块的 `selectCharacter`/`createCharacter` 设置好 `gameStore.currentCharacterId`，exploration 只需读取
- **设计对齐**：与 character/store.ts（P3-116 修复）的代理模式一致，收口 currentCharacterId 写入路径到 `gameStore.setCurrentCharacterId`，消除状态漂移风险。
- **测试适配**：
  - `test/exploration/store.test.ts` 新增 `mocks.gameStore`，mock `useGameStore`
  - `beforeEach` 重置 `currentCharacterId = null`（默认未登录状态）
  - 3 个验证持久化触发的测试用例（useCamp/revealAllCells/revealGrid-campUsed 分支）在 `init('char_1')` 前显式设置 `mocks.gameStore.currentCharacterId = 'char_1'`
- **效果**：exploration 模块的 currentCharacterId 与 gameStore 自动同步，登出时 `gameStore.setCurrentCharacterId(null)` 会自动反映到 exploration，无需各模块独立维护。
- **风险**：低。exploration 的 currentCharacterId 仅用于 persistState 守卫，改为只读 computed 后写入路径收口，行为不变。
- **遗留**：发现其他 5 个 Store（skill/log/map/quest/equipment/inventory）仍有本地 `currentCharacterId = ref`，建议后续批次统一改为 gameStore 代理（P3-153 扩展）。
