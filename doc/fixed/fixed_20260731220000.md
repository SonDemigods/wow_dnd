### P3-95. 敌人魔法普攻支持 — 需设计确认

  - 默认值兜底：`physicalAttack ?? 10` / `magicAttack ?? 5`
- [src/modules/enemy/db.ts](file:///d:/openSource/wow_dnd/src/modules/enemy/db.ts)
  - `fromStorageBase` 新增 `attackType` 字段透传，仅允许 `'physical'` / `'magical'` 值通过

- [src/data/config_mobs.ts](file:///d:/openSource/wow_dnd/src/data/config_mobs.ts)

- 配置驱动：通过 `config_mobs.ts` 为法系敌人显式配置 `attackType: 'magical'`，未配置的敌人均走物理普攻

### P3-106. item-template/cache.ts 错误缓存策略 — 需谨慎实现

**问题背景**

`UnifiedItemTemplateCacheService` 的 `load()` 失败后，`loaded` 保持 false 但 `loadingPromise` 也未重置，下次调用会复用失败的 Promise 导致永久失败。`getAll()` / `getById()` 在 `load()` 失败时直接抛异常，调用方需逐处 try-catch，与缓存层的"透明降级"语义不符。

**涉及文件**

- [src/modules/item-template/cache.ts](file:///d:/openSource/wow_dnd/src/modules/item-template/cache.ts)
  - `load()` 的 `doLoad()` 改用 `try/finally`：无论成功或失败，`finally` 都重置 `loadingPromise = null`，下次调用自动重试
  - `getAll()` 在 `load()` 失败时降级返回 `[]`，通过 `console.error` 记录错误，不向上抛出
  - `getById()` 在 `load()` 失败时降级返回 `null`，调用方按"未找到"处理
  - 补充完整的错误处理策略注释（类头与各方法）
- [test/item-template/cache.test.ts](file:///d:/openSource/wow_dnd/test/item-template/cache.test.ts)（新建）
  - 10 个测试用例覆盖：
    - `load` 成功路径（首次加载 / 二次命中缓存）
    - `load` 失败路径（loaded 保持 false / 下次自动重试）
    - `getAll` 降级（DB 故障时返回 `[]` + console.error）
    - `getById` 降级（DB 故障时返回 `null` + console.error）
    - `invalidate` 清空缓存后重新加载
    - 并发去重（3 个并发 `load` 只触发 1 次 DB 查询）

**设计决策**

- 不缓存错误：`loadingPromise` 失败后立即重置为 null，下次调用自动重试，避免短暂 DB 故障导致长期不可用
- 安全默认值：`getAll` 返回 `[]`、`getById` 返回 `null`，调用方无需 try-catch
- 显式错误感知：调用方若需感知加载失败，可直接调用 `load()` 捕获异常
- console.error 上报：保留错误日志便于运维监测，但不引入 errorReporter 依赖（缓存层应保持纯净）

### P3-113. SHA-256 迁移：calculateChecksum 改用 Web Crypto API — 延后

**问题背景**

原 `calculateChecksum` 使用 `(hash << 5) - hash + char` 的 32 位 DJB2 变种哈希算法，碰撞概率较高（约 2^-32）。备份文件若发生局部比特翻转且恰好使哈希值不变，校验会误判为"未损坏"。SHA-256 输出 256 位摘要，碰撞概率可忽略（约 2^-128），是业界标准的完整性校验算法。

**涉及文件**

- [src/modules/data/backup.ts](file:///d:/openSource/wow_dnd/src/modules/data/backup.ts)
  - `calculateChecksum` 由同步函数改为异步函数 `Promise<string>`
  - 实现改用 `crypto.subtle.digest('SHA-256', buffer)`（Web Crypto API）
  - 输入编码：`new TextEncoder().encode(str)` 转换为 UTF-8 `Uint8Array`
  - 输出格式：64 字符的 SHA-256 十六进制字符串（`bytes[i].toString(16).padStart(2, '0')`）
  - 补充完整的迁移原因、异步化原因、兼容性说明注释
  - `createBackup` 中 `calculateChecksum(data)` 改为 `await calculateChecksum(data)`
- [src/modules/data/importer.ts](file:///d:/openSource/wow_dnd/src/modules/data/importer.ts)
  - `validateBackup` 中 `reader.onload` 回调改为 `async () => { ... }`
  - `calculateChecksum(backup.data)` 改为 `await calculateChecksum(backup.data)`
- [test/data/backup.test.ts](file:///d:/openSource/wow_dnd/test/data/backup.test.ts)
  - 更新 4 个原有测试为 async 版本（`await calculateChecksum(...)`）
  - 新增 2 个测试：
    - `calculateChecksum 返回 Promise（P3-113 异步化）`：验证返回值是 Promise 实例
    - `P3-113：SHA-256 输出长度固定为 64 字符（碰撞概率 2^-128）`：5 种不同输入均输出 64 字符
  - `返回值为十六进制字符串` 测试增强为 `返回值为 64 字符的 SHA-256 十六进制字符串`，断言 `toHaveLength(64)`

**设计决策**

- 选择 SHA-256 而非 SHA-512：64 字符长度足够，性能优于 SHA-512，且为浏览器/Node 标准支持
- 异步化不可避免：Web Crypto API 的 `crypto.subtle.digest` 为异步接口，调用方 `createBackup` / `validateBackup` 均为 async 函数，await 即可
- 兼容性：浏览器 Chrome 60+/Firefox 75+/Safari 11+ 原生支持；Node 16+ 通过 `globalThis.crypto.subtle` 暴露
- 不再保留旧算法：直接替换而非保留两个函数，避免调用方误用旧的不安全版本

### P3-128. GameBootstrap 并行化：分层并行初始化 — 需分析依赖

**问题背景**

原 `GameBootstrap.initialize` 串行 await 7 个 Store 的 `initialize/init`，总耗时为各 Store IO 时间之和。经依赖关系分析，部分 Store 之间无依赖，可以并行初始化以减少总耗时。

**依赖关系分析**

```
原串行顺序：log → inventory → [注入回调] → equipment → skill → map → exploration → quest
依赖图：
  log        ← 被 exploration 依赖
  inventory  ← 被 equipment（通过回调）/ quest（通过回调）依赖
  equipment  ← 依赖 inventory 回调（Layer 1.5 注入）
  skill      ← 无外部依赖
  map        ← 被 exploration 依赖
  exploration ← 依赖 log + map
  quest      ← 依赖 inventory 回调 + exploration
```

**分层并行方案**

- **Layer 1**：`log + inventory` 并行（互不依赖）
- **Layer 1.5**：注入所有回调（同步，需在 inventory 完成后、Layer 2 前）
  - `setInventoryCallbacks`（A1/G1 + DB-1/DB-2 修复）
  - `setInventoryExternalCallbacks` / `setQuestExternalCallbacks`（ARCH-2 修复）
  - `setBossCreateFn`（阶段四 + TS-2 修复）
- **Layer 2**：`equipment + skill + map` 并行（互不依赖，equipment 依赖 Layer 1.5 注入的回调）
- **Layer 3**：`exploration`（依赖 log + map）
- **Layer 4**：`quest`（依赖 inventory 回调 + exploration）

**涉及文件**

- [src/services/GameBootstrap.ts](file:///d:/openSource/wow_dnd/src/services/GameBootstrap.ts)
  - `initialize` 方法重组为 4 层并行结构
  - Layer 1：`Promise.all([useLogStore().initialize(characterId), inventoryStore.initialize(characterId)])`
  - Layer 2：`Promise.all([useEquipmentStore().initialize(characterId), useSkillStore().initialize(characterId), useMapStore().initialize(characterId)])`
  - 补充完整的分层注释与依赖关系说明
  - 类头注释新增 P3-128 并行化方案与性能收益说明
- [test/services/GameBootstrap.test.ts](file:///d:/openSource/wow_dnd/test/services/GameBootstrap.test.ts)
  - 原 `按 log→inventory→equipment→skill→map→exploration→quest 顺序调用` 测试改为 `P3-128 并行化：按 Layer 分层调用，层内并行，层间有序`
    - 用 `Date.now()` 记录每个 Store 的调用时间戳
    - 断言层间严格有序（Layer 1 max ≤ Layer 2 min ≤ Layer 2 max ≤ exploration ≤ quest）
  - 新增 2 个并行化验证测试：
    - `P3-128：Layer 1 中 log 与 inventory 并行`：模拟 50ms IO 耗时，断言两者启动时间差 < 10ms，总耗时 < 180ms（串行 100ms + 缓冲）
    - `P3-128：Layer 2 中 equipment/skill/map 并行`：模拟 50ms IO 耗时，断言三者启动时间差 < 10ms
  - 3 个回调注入顺序测试更新注释（A1/G1 / 阶段四 / ARCH-2 修复仍保持层间有序）

**设计决策**

- 不引入 rxjs 等额外依赖：纯 `Promise.all` 实现，保持轻量
- 保持回调注入的同步语义：Layer 1.5 在 Layer 1 完成后立即同步执行，确保 Layer 2 中 equipment 调用时回调已就绪
- 不并行 exploration 与 quest：exploration 是 quest 的依赖，必须先完成
- 测试用 `Date.now()` 时间戳断言而非严格顺序数组：并行层内的相对顺序由事件循环决定，不应断言固定顺序
- 性能缓冲：Layer 1 并行测试断言 `< 180ms`（串行 100ms + 80ms 缓冲），防止 CI 环境抖动

**性能收益估算**

假设各 Store 平均 IO 耗时 50ms：
- 原串行：7 × 50ms = 350ms
- 并行后：Layer 1（50ms）+ Layer 2（50ms）+ Layer 3（50ms）+ Layer 4（50ms）= 200ms
- 理论减少约 40% 初始化耗时
