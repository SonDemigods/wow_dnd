## 一、业务逻辑修复（3 个）

### BIZ-11：skill/service.ts canCastSkill 仅检查法力 【P1·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/skill/service.ts:262-315` |
| 类型 | 业务逻辑不完整 |
| 修复状态 | 已修复 |

**问题表现**：`canCastSkill` 仅校验 `currentMana < skill.mpCost`，不检查资源系统、冷却时间、沉默状态。

**修复方案**：扩展 `canCastSkill` 签名，新增 `CanCastSkillOptions` 接口，支持以下校验维度（短路求值顺序）：
1. 沉默状态（`isSilenced`）→ 禁止施放任何技能
2. 冷却时间（`currentCooldown > 0`）→ 技能未就绪
3. 法力值（`currentMana < skill.mpCost`）→ 法力不足
4. 资源系统（`hasEnoughResource` 回调）→ 专属资源不足

向后兼容：第二个参数为 `number` 时自动包装为 `{ currentMana: number }`。

**回归测试**：`src/modules/skill/service.test.ts`（28 个用例，覆盖四维校验、顺序、兼容性）

### BIZ-19：canAcceptQuest 不检查前置任务 【P1·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/quest/service.ts:126-170` |

| 修复状态 | 已修复 |

**问题表现**：`canAcceptQuest` 仅检查等级和已存在实例，不检查前置任务（`prerequisiteQuests` 字段）。

**修复方案**：新增 `checkPrerequisiteQuests` 纯函数，遍历 `definition.prerequisiteQuests` 列表，确认每个前置任务存在实例且状态为 `completed` 或 `turned_in`。`canAcceptQuest` 在以下两条路径均调用此函数：
- 新任务接取路径
- 已放弃任务重新接取路径

**回归测试**：`src/modules/quest/service.test.ts`（34 个用例，覆盖等级、实例状态、前置任务各种组合）

## 二、架构修复（4 个）

### ARCH-14：shop/store 的 soldItems Map 操作可能不触发响应式 【P1·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/shop/store.ts:62-80, 318-351, 414-446` |
| 类型 | Vue 响应式误用 |
| 修复状态 | 已修复 |

**问题表现**：回购列表使用 `ref<Map>`，`.set()/.delete()` 不触发深层响应式。

**修复方案**：新增 `refreshSoldItems` 方法，每次修改 Map 后创建新 Map 实例整体替换：`soldItems.value = newMap`。所有写入/删除路径（出售、回购、清空）均通过此方法触发响应式更新。

### ARCH-17：useCombatState 在 composable 顶层调用 Store 【P1·已修复】

| 类型 | composables 设计 |
| 修复状态 | 已修复 |

**问题表现**：composable 顶层直接调用 `useEnemyStore()`，降低可测试性。

**修复方案**：将 `useEnemyStore()` 调用延迟到使用时，通过 getter 函数访问：

### DBG-1：88 处 console 调用残留生产 【P1·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `vite.config.ts:54-65` |
| 类型 | 日志与调试 |
| 修复状态 | 已修复 |

**问题表现**：全项目 22 个文件共 89 处 `console.log/warn/error/info/debug`，生产环境输出敏感信息。

**修复方案**：在 `vite.config.ts` 的 esbuild 配置中添加 `pure` 选项：
```typescript
esbuild: {
  pure: ['console.log', 'console.debug', 'console.info'],
}
```
生产构建时 esbuild minify 阶段自动移除这些调用，保留 `console.error`/`console.warn` 用于错误上报。

## 四、性能与数据安全修复（2 个）

### PERF-3：日志高频同步写入 【P1·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/log/store.ts:38-86, 126-138` |
| 类型 | 性能瓶颈 |
| 修复状态 | 已修复 |

**问题表现**：每次添加日志都 `await saveToDb()`，把整个 `logs.value`（最多 500 条）覆盖式写入 DB，高频 IDB 写入与战斗逻辑争用主线程。

**修复方案**：引入去抖批量持久化机制：
- 新增 `saveTimer` 模块级变量和 `SAVE_DEBOUNCE_MS` 常量（300ms）
- `scheduleSaveToDb` 标记脏数据后延迟 300ms 写入，连续多次 `addLogEntry` 只触发一次 DB 写入
- 新增 `flushSave` 同步刷新方法，用于关键时机（清空、卸载）立即触发未完成的去抖写入
