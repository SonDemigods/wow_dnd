## 修复概述

将 combat 模块对 6 个外部 Store（character / skill / enemy / quest / log / inventory）的依赖收口为单一 `ICombatContext` 接口，并通过 `IBossContext` 接口解耦 combat ↔ boss 之间的结构性耦合，使 composable 可独立测试（仅 mock 接口而非完整 Pinia Store 链路）。

## S2：ICombatContext 接口收口

### 设计要点

1. **接口最小化**：仅暴露 combat 模块实际使用的方法（已逐文件 grep 核对调用点）
2. **保持响应式**：Store 计算属性（name/hp/maxHp/attributes/effectiveStats）通过 getter 代理，避免值拷贝丢失响应式追踪
3. **集中引用**：`createCombatContext()` 是 combat 模块内唯一引用外部 Store 的位置

### 接口结构

```typescript
export interface ICombatContext {
  character: { name, classId, hp, maxHp, attributes, effectiveStats,
               takeDamage, gainExp, gainGold, handleDeath, receiveHeal, changeMp };
  skill:     { castSkill, getSkill, tickCooldowns, resetCooldowns };
  enemy:     { getEnemyById, deleteEnemy, takeDamage, createEnemy,
               getAvailableSkills, useSkill, calculateDamage, tickCooldowns };
  quest:     { onEnemyKilled };
  log:       { addLogEntry };
  inventory: { useItem, getItemInfo, addItem };
}
```

### composable 签名改造

| composable | 改造前 | 改造后 |
|------------|--------|--------|
| `useCombatState` | `()` | `(ctx: ICombatContext)` |
| `useCombatLog` | `(state)` | `(state, ctx: ICombatContext)` |
| `usePassiveSkills` | `(state, log)` | `(state, log, ctx: ICombatContext)` |
| `useEnemyAction` | `(state, log, passive?)` | `(state, log, ctx, passive?)` |
| `usePlayerAction` | `(state, log, initiative, endCombat, passive)` | `(state, log, ctx, initiative, endCombat, passive)` |
| `useInitiative` | `(state, log, enemy, boss, endCombat, passive?)` | `(state, log, ctx, enemy, boss, endCombat, passive?)` |

## S3：IBossContext 接口解耦

### 设计要点

`useBossMechanics` 原直接 import `useCharacterStore` 和 `useEnemyStore`，改造为通过 `IBossContext` 接口注入外部依赖，Boss 机制可独立测试与复用。

### IBossContext 接口

```typescript
export interface IBossContext {
  getPlayerName(): string;
  createMinion(dataId: string, level: number): Promise<EnemyInstance | null>;
  rebuildInitiativeOrder(): void;
}
```

### 循环依赖解决（R5 风险）

`bossCtx.rebuildInitiativeOrder` 需调用 `initiative.buildInitiativeOrder`，但 `initiative` 依赖 `boss`，形成循环。采用延迟绑定模式：

```typescript
// combat/store.ts
let initiativeRef: { buildInitiativeOrder: () => void } | null = null;
const bossCtx: IBossContext = {
  // ...
  rebuildInitiativeOrder: () => initiativeRef?.buildInitiativeOrder(),
};
const boss = useBossMechanics(state, log, bossCtx);
const initiative = useInitiative(state, log, ctx, enemy, boss, endCombat, passive);
initiativeRef = initiative;  // 延迟绑定
```

此模式替代了原 `boss.setInitiativeCallback(initiative.buildInitiativeOrder)` 方法，语义更清晰。

## 测试 mock 策略

采用两种策略适配新签名：

### 策略 A：createCombatContext + createTestPinia（适用于未 mock Store 模块的测试）

```typescript
// useCombatState.test.ts
const ctx = createCombatContext();
useCombatState(ctx);
```

### 策略 B：makeMockCtx 指向已 mock 的 Store（适用于已 mock Store 模块的测试）

```typescript
// usePlayerAction.test.ts / usePassiveSkills.test.ts 等
function makeMockCtx(overrides: Partial<ICombatContext> = {}): ICombatContext {
  return {
    character: {
      get name() { return characterMock.name; },  // getter 动态读取，保持响应式
      get hp() { return characterMock.hp; },
      takeDamage: characterMock.takeDamage,         // 指向同一 vi.fn 实例，断言有效
      // ...
    },
    skill: { getSkill: skillStoreMock.getSkill, ... },
    // ...
  } as unknown as ICombatContext;
}
```

**关键点**：各域方法指向已 mock 的 Store mock 对象，保证测试中对 Store mock 的断言（如 `expect(inventoryStoreMock.useItem).toHaveBeenCalledWith(...)`）仍然有效。
