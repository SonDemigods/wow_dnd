## 二、P2 一般问题修复（6 个）

### P2-1 多处使用 `any` 类型（违反 code_rule「禁止使用 any」）✅ 已修复

- **位置**：`App.vue`、`ConfigManager.vue`、`AdminForm.vue`、`admin/db.ts`、`audio/service.ts`、`base/store.ts`、`bus/types.ts` 等 11 个文件共 14 处 `any`。
- **修复方案**：
  - `App.vue`：使用 `declare global { interface Window { __gameState: Ref<GameState> } }` 扩展 Window 接口。
  - `admin/db.ts`：改用 Dexie 官方 `table()` API + `Table<Record<string, unknown>, string>` 类型断言；修复 `search` 方法 `collection.or('id')` 链式查询类型错误。
  - `bus/types.ts`：`EventCallback` 从 `(...args: any[]) => void` 改为 `(...args: unknown[]) => void`。
  - `base/store.ts`：`createQuickGetter<T extends Record<string, any>>` 改为 `<T extends Record<string, unknown>>`。
  - `audio/service.ts`：`handler as (data: any) => void` 改为 `handler as (data: unknown) => void`。
  - 新增 `AdminRecord` 类型（`Record<string, unknown>`），在 `admin/types.ts` 定义并通过 `admin/index.ts` 导出，`ConfigManager.vue` 与 `AdminForm.vue` 使用该类型替代 `any`。
  - `AdminForm.vue`：新增 `FormFieldValue` 联合类型，textarea 的 `v-model` 改为 `:value` + `@input` 解决 unknown 与 v-model 类型不兼容问题。
  - `console.ts`：Window 断言改为包含 `GameState` 联合类型。
  - `usePlayerAction.ts`：添加 `void passive;` 抑制 unused parameter 警告。
- **验证**：`npx vue-tsc --noEmit` 通过（0 errors）。

## 三、修复过程中发现并修复的源码 bug（3 个）

### BIZ-FIX-1 `inventory/db.ts` `saveItemTemplate` 把 `levelRequirement=0` 当 falsy 吞掉

- **位置**：`src/modules/inventory/db.ts:103`
- **原因**：`levelRequirement: item.levelRequirement || null` 使用 `||`，0 是合法的等级要求但被当作 falsy 转为 null。读取端 `mapToItem` 用 `??`（注释明确「0 是合法的等级要求」），读写不一致。
- **修复**：改为 `?? null`，与读取端语义一致。
- **发现路径**：P1-1 `test/db/inventory.test.ts` 测试 `levelRequirement=0` 保留场景时暴露。

### BIZ-FIX-2 `quest/db.ts` `saveQuestDefinition` 漏写 `prerequisiteQuests` 字段

- **位置**：`src/modules/quest/db.ts` `saveQuestDefinition` 的 `put()` 调用。
- **原因**：`put()` 入参对象缺少 `prerequisiteQuests: definition.prerequisiteQuests`，导致 Dexie 持久化时该字段未写入；读取端 `_mapToDefinition` 取到 `undefined`，前置任务链断裂。
- **修复**：在 `put()` 入参中补齐该字段。
- **发现路径**：P1-1 `test/db/quest.test.ts` 测试往返一致性时暴露。

### BIZ-FIX-3 `useCombatState.ts` `resetState` 漏重置 `initiativeOrder` 和 `currentInitiativeIndex`

- **位置**：`src/modules/combat/composables/useCombatState.ts` `resetState()`。
- **原因**：`resetState` 注释声明「重置所有战斗状态到初始值」，但遗漏了 `initiativeOrder`（先攻顺序数组）和 `currentInitiativeIndex`（当前行动索引），导致 `cleanup` 后残留上一场战斗的行动顺序数据。
- **修复**：在 `resetState` 中补齐 `initiativeOrder.value = []; currentInitiativeIndex.value = 0;`。
- **发现路径**：P1-3 `test/combat/useCombatState.test.ts` 测试 `resetState` 行为时暴露。

## 四、记录但未修复的源码行为问题（1 个）

### BIZ-NOTE-1 `usePassiveSkills.ts` `applyHeal` 中 `damage=0` 时按 maxHp 百分比治疗（与注释不符）

- **位置**：`src/modules/combat/composables/usePassiveSkills.ts` `applyHeal` 方法。
- **表现**：注释说「按伤害百分比吸血」，但代码 `context?.damage && context.damage > 0` 为 false 时走 else 分支按 `maxHp × value` 治疗。即 `damage=0` 时反而会治疗（按 maxHp 百分比），与「吸血」语义不符。
- **当前处理**：未修复（属于业务逻辑改动，超出「测试覆盖」修复范围）。测试用例已匹配源码当前行为并加注释说明。
- **建议**：后续单独评估是否调整源码逻辑（damage=0 时不应触发吸血）或修订注释。
