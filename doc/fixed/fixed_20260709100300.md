## 概述

本次归档记录第三轮多代理深度检查（重点聚焦架构一致性与业务逻辑正确性）发现的 7 个问题的处理。涉及核心玩法循环（collect 类型任务完全失效）、经济原子性（购买部分成功白嫖）、数据丢失防御（掉落/奖励静默丢失）、战斗状态隔离（技能冷却跨战斗残留）、防御性加固（战斗状态重置、音频服务重建）。修复后 `current.md` 第三轮发现的问题已全部清零。

## 一、P1 严重修复（1 个）

### P1-1 collect 类型任务完全无法完成【P1·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/quest/store.ts`（onItemCollected 定义）、`src/modules/inventory/store.ts`（addItem 未触发任务进度） |
| 类型 | 核心玩法循环断裂（BIZ-1） |

**问题**：`onItemCollected(itemId, amount)` 在 quest/store.ts 定义并导出，但全工程无任何实际调用方。`inventory/store.ts` 的 `addItem` 全程未调用 `onItemCollected`。导致 collect 类型任务（如默认任务 `quest_collect_herbs` 采集 15 株草药）永远无法完成——进度永远是 0。对比 `onEnemyKilled` 在 `combat/store.ts` 被正确调用，collect 类型完全遗漏。

**附加问题**：`acceptQuest` → `generateQuestInstance` 初始化所有 `progress.current = 0`，无"检查现有库存"逻辑——即使修复了调用，接任务前已持有的物品也不会被计入初始进度。

**修复方案**（两处联动）：
1. `inventory/store.ts` 的 `addItem` 末尾（return 前）调用 `useQuestStore().onItemCollected(itemId, added)`，触发 collect 任务进度。
2. `quest/store.ts` 的 `acceptQuest` 中，`generateQuestInstance` 之后对 collect 类型目标扫描当前背包数量作为初始进度：
   ```ts
   const inventoryStore = useInventoryStore();
   const hasCollectObjective = definition.objectives.some(obj => obj.type === 'collect' && obj.itemId);
   if (hasCollectObjective) {
     instance.progress = instance.progress.map(prog => {
       const obj = definition.objectives.find(o => o.key === prog.objectiveKey);
       if (obj?.type === 'collect' && obj.itemId) {
         const owned = inventoryStore.inventory
           .filter(slot => slot.itemId === obj.itemId)
           .reduce((sum, slot) => sum + slot.count, 0);
         return { ...prog, current: Math.min(owned, prog.target) };
       }
       return prog;
     });
   }
   ```

## 二、P2 一般修复（3 个）

### P2-1 购买流程原子性缺陷：部分成功时白嫖物品【P2·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/shop/store.ts`（buyItem） |
| 类型 | 经济原子性（BIZ-2） |

**问题**：`buyItem` 流程为：扣除全额金币 → `addItem` → 若 `added < quantity` 返还**全额** `totalPrice` 并 return false。但 `addItem` 内部在 `added > 0` 时已执行 `inventory.value = newInventory; persistInventory()`——部分物品已入包并落盘。背包部分满时，玩家保留 `added` 个物品 + 拿回全部金币，相当于白嫖这部分物品。

**修复方案**：将 `const totalPrice` 改为 `let totalPrice`，重写部分成功逻辑：按未添加比例返还金币，并继续后续流程（商店库存/日志按实际购买量处理）：
```ts
const added = inventoryStore.addItem(itemId, quantity);
if (added < quantity) {
  const refundAmount = shopItem.price * (quantity - added);
  if (refundAmount > 0) {
    await characterStore.gainGold(refundAmount);
  }
  if (added === 0) return false;
  useToast().show({ message: `背包空间不足，仅成功购买 ${added} 件`, type: 'warning', duration: 2500 });
  quantity = added;
  totalPrice = shopItem.price * added;
}
```

### P2-2 handleLoot 与任务奖励不检查 addItem 返回值，背包满时静默丢失【P2·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/combat/composables/usePlayerAction.ts`（handleLoot）、`src/modules/quest/store.ts`（_grantQuestRewards） |
| 类型 | 数据丢失防御（BIZ-3） |

**问题**：
- `handleLoot`：`addItem(drop.itemId, amount)` 不检查返回值，仍用原始 `amount` 记录日志——玩家实际少拿了，日志却显示全额获得，且无任何"背包已满"提示。
- `_grantQuestRewards`：`addItem(item.itemId, item.count)` 同样不检查返回值，任务奖励物品满包时静默丢失。

**修复方案**：两处均检查 `addItem` 返回值，使用 `actualAmount` 替代原始数量记录日志，未完全添加时 toast 提示玩家：
- `handleLoot`：`const actualAmount = useInventoryStore().addItem(drop.itemId, amount);` 并在 `actualAmount < amount` 时 toast 警告，日志记录 `actualAmount`。
- `_grantQuestRewards`：检查 `added = addItem(...)`，`added < item.count` 时 toast `背包已满，任务奖励物品仅获得 ${added}/${item.count}`。

### P2-3 技能冷却跨战斗残留【P2·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/skill/store.ts`、`src/modules/combat/store.ts`（startCombat） |
| 类型 | 战斗状态隔离（BIZ-4） |

**问题**：`skill/store.ts` 的 `cooldowns` 是全局持久状态（跨战斗不自动清空）。`tickCooldowns()` 仅"递减 1"。`combat/store.ts` 的 `startCombat` 和 `endCombat` 均未重置 `skillStore.cooldowns`。`skillStore.reset()` 虽清空 cooldowns 但注释明确"用于角色重置、切换存档等场景"——非战斗生命周期方法。一场战斗中使用了冷却 5 回合的技能（剩 3 回合），战斗在第 2 回合结束，进入下一场战斗时该技能仍冷却 2-3 回合。回合制下冷却以"回合"为单位，跨战斗残留不合理。

**修复方案**：
1. `skill/store.ts` 新增 `resetCooldowns()` 方法（区别于全量 `reset()`，仅清空冷却状态）：
   ```ts
   function resetCooldowns(): void {
     cooldowns.value = {};
   }
   ```
2. `combat/store.ts` 的 `startCombat` 中调用 `useSkillStore().resetCooldowns()`。
3. 同步更新 `test/combat/store.test.ts`：为 `useSkillStore` mock 注入包含 `resetCooldowns` 的 stub。

## 三、P3 轻微修复（2 个）

### P3-1 combat startCombat 未防御性 reset，非正常流程下定时器可能残留【P3·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/combat/store.ts`（startCombat） |
| 类型 | 防御性加固（LOGIC-1） |

**问题**：`startCombat` 直接覆盖状态字段，未先调用 `state.reset()`。正常流程下 `endCombat → cleanup → resetState` 链路完整无泄漏；但若上一场战斗未正常调用 `endCombat`（组件异常卸载等边缘场景），旧的 `turnTimerId`/`bossIntroTimerId` 可能残留并向新战斗 UI 推送过期数据。

**修复方案**：在 `startCombat` 第一行加入防御性 `state.reset()` 调用：
```ts
function startCombat(enemiesData: EnemyInstance[]): void {
  // P3-1：防御性重置，防止上一场战斗未正常 endCombat 时定时器/状态残留
  state.reset();
  state.combatId.value = generateCombatId();
  ...
}
```

### P3-2 audio service destroy 后无法重新 init【P3·已修复】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/audio/service.ts`（destroy） |
| 类型 | 资源生命周期（LOGIC-2） |

**问题**：`destroy()` dispose 了所有 Tone.js 节点但未重置 `initialized`/`contextReady`/`reverbReady` 等标志。destroy 后再调用 `init()` 会因 `initialized === true` 直接 return，不重建节点，后续 `playSfx` 调用已 dispose 节点会抛异常。当前 `destroy()` 全工程无调用方，实际运行无影响，但作为公开 API 存在隐患（HMR 场景或后续扩展时可能踩雷）。

**修复方案**：在 `destroy()` 末尾重置状态标志：
```ts
this.initialized = false;
this.contextReady = false;
this.reverbReady = false;
this.currentBgmScene = null;
this.synthScheduleTimes.clear();
```

## 四、P3 评估暂缓（1 个）

### P3-3 endCombat 中角色操作 fire-and-forget 未 await【P3·评估暂缓】

| 项 | 内容 |
|----|------|
| 位置 | `src/modules/combat/store.ts`（endCombat L131-132、L169） |
| 类型 | 时序一致性（LOGIC-3） |
| 决策 | 评估后暂缓，不修改代码 |

**问题**：`endCombat` 中 `characterStore.gainExp(totalExp)` / `gainGold(totalGold)` / `handleDeath()` 都是 fire-and-forget（未 await）。这些方法内部都 `await persistCharacter()`，最终一定会持久化，但 `log.saveLogs()` 和 `eventBus.emit(COMBAT_END)` 可能在持久化完成前执行。若用户在战斗结束瞬间关闭页面（极小概率窗口），理论上有持久化未完成的风险。

**暂缓理由**：
1. `endCombat` 是同步函数（`function endCombat(result: CombatResult): void`），全工程有 **12 处**同步调用方（console.ts、usePlayerAction.ts、useInitiative.ts）。改为 `async` 需同步更新全部调用方，改动面过大，违反"最小修改"与"避免过度工程"原则。
2. 实际影响极小：P3 级别标注为"可选改进"，且 current.md 明确"实际影响极小"。持久化操作在微任务队列中执行，正常场景下页面不会在毫秒级窗口内关闭。
3. 收益与风险不匹配：大范围签名变更带来的回归风险（12 处调用方需逐个确认 await 上下文）远高于修复一个极小概率的时序窗口。

**建议**：若未来重构战斗结束流程（如引入战斗结算动画延迟），可顺带将 `endCombat` 改为 async 并统一 await；当前保持同步实现。

## 六、本轮检查通过的维度（交叉验证确认）

以下维度经多代理深度核查未发现新问题：

1. **Store 间无循环依赖**：依赖关系为 DAG 结构，`log` 与 `character` 是底层被依赖节点。`inventory` ↔ `equipment` 看似双向，但 inventory 通过 `crossModuleQuery` 只读查询 equipment DB，不直接 import equipment store。
2. **探索 Store 事件监听器无重复注册**：`setupCombatListener` 中 `clearGroup('exploration')` 在 `onGroup` 前正确执行。
3. **装备 reapplySetBonuses 调用时机完整**：`equipItem`/`unequipItem`/`initialize`/`reset` 四个入口均正确调用。
4. **角色属性持久化覆盖完整**：所有 character store Action 均正确 `await persistCharacter()`。
5. **敌人效果容器已正确清理**：`endCombat` 和 `startCombat` 均清空 `enemyEffects`。
6. **普通敌人不掉落物品**：属设计限制非意外 bug。
7. **架构一致性良好**：五层结构完整，跨模块依赖通过 index.ts 公共入口，service 层无 DOM 操作。
8. **代码规范**：无实际 `any` 使用，无空 catch 块，.vue 文件均使用 `<script setup lang="ts">`。
