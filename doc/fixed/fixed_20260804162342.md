## 修复概述

商店系统在 2026-08-03 全维度复查中共暴露 3 类核心缺陷，并衍生出 2 处代码一致性 bug，叠加导致装备获取渠道断裂、经济平衡参数被绕过、UI 组件臃肿三大隐患。本次修复按 [plan.md](file:///d:/openSource/wow_dnd/plan.md) 的三个阶段推进：

1. **阶段一（P3-158）**：价格计算 100% 读取 `config/inventory.ts` 常量，消除 service 层硬编码倍率
2. **阶段二（P3-161）**：新增 `equipment` 商店类型，支持 weapon/armor 上架，补全装备获取渠道
3. **阶段三（P3-163 商店部分）**：ShopPopup 抽离 2 个业务 Composable，主组件 script 从 363 行降至 ~152 行

### 修复前现状（数值偏差核心证据）

| 稀有度 | `RARITY_PRICE_MULTIPLIER`（config） | `getRarityMultiplier`（service 硬编码） | 偏差 |
|--------|------------------------------------|--------------------------------------|------|
| uncommon | 2.5 | 2.0 | -20% |
| epic | 15 | 10.0 | -33% |
| legendary | 50 | 20.0 | -60% |

| 稀有度 | `RARITY_SELL_DISCOUNT`（config） | `calculatePrice` 出售价（service 硬编码 5 折） | 偏差 |
|--------|--------------------------------|----------------------------------------|------|
| epic | 0.3 | 0.5 | +67% |
| legendary | 0.25 | 0.5 | +100% |

> 结论：硬编码导致 epic/legendary 商品的购买价被低估、出售价被高估，玩家出售稀有装备时获益过高，破坏经济平衡。

### 修复后状态

- 价格计算 100% 读取 config 常量，平衡性调整只需改 config 无需动 service
- 新增 `equipment` 商店类型 + 2 家装备商店（铁匠铺/防具商行），weapon/armor 可上架
- ShopPopup 分类筛选按商店类型动态生成，消除 weapon/armor/misc 死分类
- ShopPopup 业务逻辑抽离为 `useShopTransactions` + `useGoldFlash` 两个独立可测试 Composable

## 阶段一：价格计算与配置常量对齐（P3-158）

### 修改 `src/modules/shop/service.ts`

**修改点 1**：引入 config 常量

```ts
import { RARITY_PRICE_MULTIPLIER, RARITY_SELL_DISCOUNT } from '@/config/inventory';
```

**修改点 2**：重写 `getRarityMultiplier`，改为读取 `RARITY_PRICE_MULTIPLIER`

```ts
function getRarityMultiplier(rarity: string): number {
  const multipliers = RARITY_PRICE_MULTIPLIER as Record<string, number>;
  return multipliers[rarity] ?? 1.0;
}
```

**修改点 3**：重写 `calculatePrice`，出售价改为按稀有度读取 `RARITY_SELL_DISCOUNT`

```ts
export function calculatePrice(itemTemplate: Item, isBuyPrice = true): number {
  const baseValue = itemTemplate.value || 0;
  const rarityMultiplier = getRarityMultiplier(itemTemplate.rarity);
  const buyPrice = Math.round(baseValue * rarityMultiplier);
  if (isBuyPrice) return buyPrice;

  const sellDiscount = getSellDiscount(itemTemplate.rarity);
  return Math.round(buyPrice * sellDiscount);
}
```

**修改点 4**：新增 `getSellDiscount`，按稀有度递减折扣

```ts
function getSellDiscount(rarity: string): number {
  const discounts = RARITY_SELL_DISCOUNT as Record<string, number>;
  return discounts[rarity] ?? 0.5;
}
```

更新断言对齐 config 真实值：
- uncommon 倍率：2.0 → 2.5（100 → 250）
- epic 倍率：10.0 → 15（1000 → 1500）
- legendary 倍率：20.0 → 50（2000 → 5000）
- 出售价断言改为按 `RARITY_SELL_DISCOUNT` 折扣（uncommon=0.4 / rare=0.35 / epic=0.3 / legendary=0.25）
- 四舍五入取整：33 × 2.0 = 66 → 33 × 2.5 = 82.5 → 83

新增联动测试：

```ts
export function useGoldFlash() {
  const goldFlash = ref(false);
  let timerId: ReturnType<typeof setTimeout> | null = null;

  function trigger() {
    goldFlash.value = true;
    if (timerId !== null) clearTimeout(timerId);
    timerId = setTimeout(() => { timerId = null; goldFlash.value = false; }, 500);
  }

  onUnmounted(() => { if (timerId !== null) clearTimeout(timerId); });
  return { goldFlash, trigger };
}
```

## 设计决策

### 1. 配置集中化而非 service 层兜底

`getRarityMultiplier` 与 `getSellDiscount` 直接读取 `RARITY_PRICE_MULTIPLIER` / `RARITY_SELL_DISCOUNT`，仅对未识别稀有度保留 `?? 1.0` / `?? 0.5` 容错。平衡性调整只需改 config，service 层无任何硬编码数字字面量，从根源消除"改 config 不生效"的隐患。

### 2. equipment 共用类型而非细化 weapon/armor

两家装备商店（铁匠铺/防具商行）均使用 `equipment` 类型，service 层会同时上架 weapon/armor。当前阶段共用 `equipment` 足够，如未来需区分武器店与护甲店，可将 `ShopType` 进一步细化为 `'weapon' | 'armor'`，`Record<ShopType, ItemType[]>` 类型会强制补齐映射。

### 3. 分类动态生成而非硬编码常量数组

`categories` 改为 computed，基于 `SHOP_TYPE_ITEM_TYPE_MAP[config.type]` 动态生成，从根源消除"商店不售卖该类型但分类标签存在"的死分类问题。新增商店类型时分类自动跟随，无需手动同步。

### 4. Composable 拆分参照 combat 模式

`useShopTransactions` 接收 store 引用作为参数（延迟绑定），参照 combat 模块 `initiativeHolder`/`playerHolder` 模式，避免直接 import store 导致的循环依赖与测试隔离问题。`onTransactionSuccess` 回调注入金币闪烁触发，解耦交易逻辑与动画逻辑。

### 5. 出售价折扣按稀有度递减

`RARITY_SELL_DISCOUNT` 按稀有度递减（common=0.5 → legendary=0.25），稀有度越高出售折扣越低，避免玩家靠出售稀有装备套利，这是设计意图而非 bug。

## 风险与缓解

| 风险项 | 等级 | 缓解措施 |
|--------|------|----------|
| 价格数值变化影响存档中已生成的 ShopItem.price | 低 | ShopItem.price 在生成时计算并持久化，旧存档保留旧价格，刷新后采用新价格。可接受 |
| `RARITY_SELL_DISCOUNT` 改为按稀有度递减后玩家出售稀有装备收益降低 | 低 | 这正是设计意图，避免套利 |
| DB 中已有商店配置缺少 equipment 类型 | 低 | `loadShopConfigs` 已有"DB 为空则播种"逻辑；已存在 DB 不会自动补齐，需在版本迁移脚本中处理（非本次范围） |
| 装备物品池若不足（P3-135 未补齐）装备商店商品稀少 | 中 | 与 P3-135 协同推进，或装备商店暂不上线直到物品池补齐 |
| Composable 拆分破坏现有响应式依赖 | 低 | 参照 combat 模块延迟绑定模式，store 引用通过参数传入；32 个 Composable 测试覆盖核心分支 |
